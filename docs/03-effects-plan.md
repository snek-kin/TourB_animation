# 03 · План цифровых эффектов

Статусы: **Есть** — реализовано и проверено в браузере (программный рендер); **План** — только техническое решение.
Бюджеты ниже — **целевые ориентиры для проверки на реальном железе**, а не измеренные значения.

| # | Эффект | Статус | Техника | Зависимости |
|---|---|---|---|---|
| 1 | Матричный цифровой дождь | **Есть** `MatrixRain` | `Points` + `ShaderMaterial`; вся анимация на GPU (uTime), глифы из canvas-атласа (цифры, символы, Ң Ө Ү); затухание у краёв, вдали и **вплотную к камере** | — |
| 2 | Частицы собирают интерфейс | **Есть** `ParticleMorph` (прототип) | цель — точки из любого canvas-рисунка (`samplePointsFromCanvas`); траектория — кривая Безье с изгибом на частицу; задержка по x → сборка слева направо; `morphTo()` стартует из текущей формы (без скачка) | — |
| 3 | Город → цифровая карта | План | см. ниже | модель Бишкека с зданиями отдельными мешами |
| 4 | Плавающие фото и карточки событий | **Есть** карточка `FloatingCard`; фото-пузыри — План | карточка: canvas-текстура + billboard; фото: `InstancedMesh` + атлас | реальные фото с правами |
| 5 | Голографические элементы | План | см. ниже | `CSS3DRenderer` (по необходимости) |
| 6 | Превращение объект → объект (match cut) | План | см. ниже | `MeshSurfaceSampler` |
| 7 | Светящиеся маршруты и маркеры | Маркеры **Есть** `GlowMarker`; маршруты — План | маркер: шейдер луча и «ряби»; маршрут: `TubeGeometry`/`Line2` + бегущий импульс | `Line2`-семейство из `three/addons` |

Недостающие аддоны копируются в `vendor/` добавлением строки в `tools/vendor.mjs` (подтверждено тестом замкнутости импортов).

## Вход камеры в смартфон (принцип A)

1. Смартфон — своя геометрия (скруглённый бокс + плоскость экрана), экран — `CanvasTexture`/`VideoTexture` с интерфейсом TourB.
2. Камера летит по рельсе к центру экрана, `near` временно уменьшается (0.01), чтобы не обрезать экран вплотную.
3. На последних 20 % пути экран затемняется (uniform яркости), «дождь» из эффекта 1 включается вокруг камеры
   (`followCamera` + рост `uOpacity`).
4. Частицы (эффект 2) собирают интерфейс **из тех же точек**, из которых нарисован экран телефона
   (`samplePointsFromCanvas` на том же canvas) — это и есть преемственность формы.
5. Телефон не должен быть узнаваемой марки.

## Город → цифровая карта (принцип B)

- У зданий общий материал-«реальный» и материал-«цифровой» (тёмный + контур `EdgesGeometry`/`LineSegments`).
  Переход — uniform `uReveal` с волной от центра (расстояние от точки, плюс шум); реализуется через
  `onBeforeCompile` поверх `MeshStandardMaterial` (discard по порогу) — свой шейдер с нуля не нужен.
- Дороги — отдельный меш линий; в «цифровой» фазе по ним бежит импульс (`uTime` + позиция вдоль линии).
- Маркеры (`GlowMarker`) и карточки (`FloatingCard`) поднимаются с задержкой от расстояния до камеры.
- **Требование к модели:** здания, дороги и вода — отдельные узлы/меши (иначе волну не пустить). Это нужно
  указать при заказе/создании `env.bishkek.city`.
- Риск: полный город в двух материалах = двойная нагрузка → в «цифровой» фазе реальные материалы отключаются.

## Голографический интерфейс (принцип C — интерфейс выходит в мир)

Два слоя по задачам:
- **в мире** (карточка превращается в здание, карта «материализуется» перед туристом) — меши с Fresnel-шейдером
  (прозрачность растёт к краю) и аддитивным смешиванием: дёшево, ложится в 3D-сцену, корректно перекрывается;
- **текст и мелкая типографика** — HTML-оверлей поверх canvas либо canvas-текстура; `CSS3DRenderer` брать только если
  нужен реальный HTML внутри 3D (второй рендерер и проблемы с глубиной — осознанная цена).

## Match cut: объект → объект (раздел 3 брифа)

Три приёма, комбинируются:

| Приём | Суть | Для каких переходов из брифа |
|---|---|---|
| **A. Синхронизированная подмена** | в точке перехода два прокси-объекта с совпадающими позицией, масштабом и поворотом на экране; GSAP ведёт их общий transform, оригинал скрывается, цель появляется | кнопка конвертера → колесо автобуса; монета → солнце; карточка жилья → окно здания |
| **B. Морфинг вершин** | две геометрии с одинаковым числом вершин (пересэмплировать), `morphTargets` | маркер → вершина горы |
| **C. Морфинг частиц** | точки на поверхности объекта A (`MeshSurfaceSampler`) → точки объекта B через `ParticleMorph.morphTo()` | универсальный запасной вариант; «звуковая волна → эффект звука» |

`TransitionManager` уже имеет контракт `async fn({from, to, swap, app})` — реальный `matchCut` пишется в Phase 2
на приёме A (он дешевле всего и точнее всего выдерживает «непрерывность»). Для «переведённый текст → уличная
табличка» нужен текст в текстуре обоих объектов с одинаковой раскладкой.

## Маршруты и маркеры

`GlowMarker` готов (булавка, луч, рябь на земле; общие геометрии, свои uniforms). Маршруты: `TubeGeometry` по
Catmull-Rom кривой (толщина мира) или `Line2` (толщина в пикселях), шейдер — смещение «пунктира» по `uTime`.
Цвет и яркость берутся из палитры `config.js`.

## Бюджет производительности (цели)

| Параметр | Цель |
|---|---|
| Частота кадров | 50–60 FPS на целевом ноутбуке/проекторе; автоснижение разрешения ниже 50 |
| Draw calls | ≤ 300 на кадр (панель отладки: `D`) |
| Треугольников в кадре | ≤ 1.5 млн |
| Частиц | 5–10 тыс. в `ParticleMorph`, ≤ 6 тыс. точек глифов в дожде (сейчас 360 колонок × 16) |
| Текстуры | ≤ 2048 px для «героев», ≤ 1024 для реквизита; общий бюджет VRAM — сначала измерить |
| Постобработка | не более одного прохода bloom, при необходимости — на половинном разрешении |

Все числа — гипотезы для проверки в Phase 2 на реальной машине, где будет показ.
